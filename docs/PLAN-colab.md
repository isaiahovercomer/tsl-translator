# 第二步規劃：用 Colab 訓練骨架辨識模型（2026-11-26，v0.13.0 時寫）

## 為什麼要訓練模型
現在的「手語 → 中文」是 **DTW 比對**：每個詞只有辭典的 1 筆示範（中正辭典 3488 筆、2844 詞），拿鏡頭比的那段跟每筆示範算距離。
問題：
- 一個詞只有一個人、一種速度的示範，換人比、比快一點、角度不同就認不出來。
- 手機前鏡頭解析度低、手常被切到，DTW 對雜訊很敏感。
- 詞多（全部 2844 個）就慢、也容易認錯 → v0.13 先用「情境」縮小詞彙應急。

訓練過的模型可以從「很多人、很多次」的資料學到哪些差異不重要，通常比 DTW 準很多（Kaggle 2023 Google 美國手語比賽：同樣只用 MediaPipe 骨架，單詞辨識 250 詞 top-1 約 80～90%）。

## 模型設計（骨架進、詞出；在手機瀏覽器跑）
- **輸入**：跟現在一樣的 82 點骨架（身體 15＋雙手 42＋臉 25），每秒 15 格，用 core.js 同樣的正規化（以兩肩中點、肩寬為基準）。鏡頭端完全不用改，訓練資料和實際使用是同一套 MediaPipe，不會有落差。
- **第一階段：單詞分類器**（取代 DTW）
  - 1D 卷積＋小型 Transformer（Kaggle 冠軍做法的縮小版），約 1～2M 參數。
  - 輸出每個詞的機率 → 直接給「前 3 個候選」（v0.13 的 AI 挑詞照用）。
  - 加一個「不是手語」類別（抓頭、推眼鏡、手放著）減少亂認。
- **第二階段：連續辨識（CTC）**
  - 整句骨架 → 每格輸出詞機率，CTC 解碼成詞序列；不必切段，比 v0.13 的「邊比邊找詞」更穩。
  - 需要有 gloss 標註的整句資料（見下面資料 B）。
- **匯出**：PyTorch → ONNX → int8 量化（約 2～4 MB）→ 網站用 onnxruntime-web（WASM／WebGPU）跑；每段推論手機約 5～20 ms。放 `models/tsl-recog-<版本>.onnx`＋`labels.json`，網站設定可切回 DTW 比較。

## Colab 筆記本（`colab/tsl_recog_train.ipynb`，下次做）
1. 掛 Google 雲端硬碟、clone repo（讀 `corpus/`）。
2. 讀資料：`corpus/signs/**`（辭典）＋收集到的骨架（雲端硬碟 `tsl-collect/`）＋網站「改正」存下的語料。
3. 前處理＋資料增強：時間伸縮（0.7～1.4 倍）、左右鏡像（左撇子）、小角度旋轉／縮放／平移、隨機遮掉手指或整隻手（模擬手被切到）、加雜訊。
4. 訓練：**依「比的人」分組**切訓練／驗證（同一個人不能同時在兩邊，才知道換人準不準）；免費 T4 GPU，1 萬筆資料約 10～30 分鐘。
5. 評估：每個情境（寒暄／聚會／召會）各自的 top-1、top-3 準確率；混淆最嚴重的詞列出來（要補資料的就是它們）。
6. 匯出 ONNX＋int8，用 `GITHUB_TOKEN` 推到 repo `models/`（同 `tsl_realistic.ipynb` 的做法）。

## 需要收集哪些資料（最重要）
| | 內容 | 數量目標 | 怎麼收 |
|---|---|---|---|
| **A. 核心詞彙單詞** | 三個情境的常用詞（`js/scenes.js`，約 300 詞）＋召會用語（下面清單） | 每詞 **≥ 20 次、≥ 5 位不同的人**；先做 100 個最常用的詞 | 網站加「收集模式」：畫面出詞卡 → 對前鏡頭比 3 次 → 只存骨架（不存影像） |
| **B. 整句（有 gloss 標註）** | 情境裡常說的短句（2～6 個詞），例如「你／名字／什麼」「明天／聚會／幾點」 | 300～500 句，每句 ≥ 3 人 | 收集模式出句卡（手語詞序），比完一句手放下 |
| **C. 不是手語** | 抓頭、推眼鏡、拿手機、手放桌上、講話時手自然擺動 | 每人 1～2 分鐘 | 收集模式「自然動作」錄一段 |
| **D. 辭典例句影片** | 中正辭典 546 句例句（已經有 gloss，只差骨架） | 546 句 | `tools/ccu_dict.py` 加抽例句影片骨架（Actions 跑） |
| **E. 江啟禎頻道** | 召會用語整句＋燒在畫面上的字幕（OCR） | 先 20 支 | 等 YT_COOKIES 重新匯出；字幕↔手勢弱監督對齊，人工確認後當 A／B 資料 |

**召會用語（辭典缺，要自己錄）**：弟兄、耶穌、基督、聖經、召會、聚會、小排、主日、晨興、讀經、禱讀、詩歌、讚美、恩典、福音、傳福音、受浸、擘餅、阿們、哈利路亞、生命、靈、聖靈、喜樂、配搭、服事、長老、交通（召會用法）。

**錄的條件要多樣**（模型才不會只認得一種畫面）：手機前鏡頭、直拿／立在桌上、白天／晚上燈光、不同背景、坐著／站著、比快／比慢、慣用左手的人。

**授權**：只存骨架點（看不出臉、看不出是誰），但仍請每位參與者勾選同意（用途：訓練手語翻譯模型、放在 GitHub 公開語料）。

## 建議順序
1. ✅ v0.14.0 已加「收集模式」（上傳到 repo 的 collect 分支，需在 Cloudflare 設 GH_COLLECT_TOKEN）——先請 3～5 位弟兄姊妹各錄 100 個核心詞。
2. 辭典例句骨架（D）用 Actions 抽。
3. Colab 第一階段單詞模型 → 網站切換「模型／DTW」實測比較。
4. 資料夠了再做第二階段 CTC 整句。

# 附：手譯員手指與表情更精確（使用者 2026-11-26 問）
**檢查結果**：`tools/eval_fingers.py` 量手譯員每根手指的彎曲角度跟骨架資料比，平均差約 19°（中位數 22°）——手譯員大致有照資料比；
不準的主要原因是**資料本身**：辭典影片用 MediaPipe 抽的手指，彎進掌心、手指互相擋住、朝鏡頭的手指，深度（z）常常錯，
看起來就是手指伸直或方向怪。試過加關節限制（手指只能往掌心彎），跟資料的差距反而變大（24.9°），所以預設不開（`#fingerlimit` 可試）。

**更精確的做法（都在 Colab 重新抽骨架，網站播放端只要小改）**：（v0.14.0 已做 1 的 3D 手點版本＋2 的表情係數：`colab/tsl_reextract.ipynb`）
1. **手指：WiLoR 或 HaMeR（3D 手部模型，輸出 MANO 每個指節的旋轉角）**——專門處理握拳、手指互擋，比 MediaPipe 準很多。
   直接把指節旋轉套到 VRM 手指骨頭，不用再從點的方向去猜。辭典 3488 筆重抽，T4 約數小時（可分批、續跑）。
2. **表情：MediaPipe FaceLandmarker 的 52 個 ARKit 表情係數（blendshapes）**——直接給「眉毛上揚、皺眉、嘟嘴、鼓頰、眯眼」等數值，
   比現在用 25 個臉部點推算準；台灣手語的非手部標記（疑問、否定、程度）靠這些。套到 VRM：常用的對到 VRoid 的 Fcl_ 表情，
   要完整 52 個得在 VRoid／Unity 給手譯員加 Perfect Sync 表情（可之後再做）。
3. **身體：** 換 RTMW（全身 133 點）或提高抽骨架的解析度（現在辭典影片手很小）。
4. 存檔格式：語料 json 加 `hands_rot`（每格 2×15×3）與 `face_bs`（每格 52 個），舊欄位保留，播放端有新欄位就用。
